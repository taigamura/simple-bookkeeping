## はじめに

個人で Suito（すいとう）というカレンダー型の家計簿アプリを作っている。Expo（React Native）+ TypeScript で書いていて、アカウント登録なし、広告なし、データはすべて iPhone の中だけ、という方針で出している。

家計簿が続かない一番の理由は、記録が面倒なことだと感じている。そこで 1.1.0 では「Suito AI」として、Apple の Foundation Models（端末内で動く言語モデル）を使った機能を入れた。

React Native のアプリから端末内モデルを呼ぶ例はまだ少ないと思うので、設計で考えたことと、途中でやり直したことをまとめておく。なお、実装の多くは Claude Code と一緒に書いている。

## Suito AI でできること

Apple Intelligence に対応した iPhone では、次の機能が使える。

- 入力欄に「昨日 スタバ 620」と書くと、金額・カテゴリ・日付・メモが埋まる（保存はユーザーが押す）
- オーブを長押しして話すと、同じように入力画面が埋まる
- レシートを撮ると、OCR で読んだ内容から入力画面が埋まる
- 先月のふりかえりの手紙、月末の着地予想などの一言
- 自分の家計について質問できる「Ask」

[スクショ：入力欄が埋まる様子 / オーブ / ふりかえりカード]

Siri と Spotlight の連携は、iOS 26 の iPhone ならモデルなしで動く。Siri から記録を追加したり、期間の収支やカテゴリ別の支出を聞いたりできる。

## JS と Swift の境界は 1 つにした

Swift 側はローカルの Expo モジュール（`modules/suito-ai`）として書いた。以前作った音声メモアプリで使った Foundation Models のモジュールを土台にしている。

JS からはすべて `SuitoAi` というインターフェース 1 つを通す。実装は 3 つあり、iOS の Swift モジュール、Web と E2E テスト用の決まった答えを返すフェイク、それと全部オフの状態である。

Playwright で画面の位置やスクリーンショットを確認するとき、モデルの答えが毎回変わると比較ができない。境界を 1 か所にしておくと、フェイクを差し込むだけで済む。複雑な入力は JSON 文字列で渡し、Swift 側は Codable で受けて TS の型と 1 対 1 にしている。

## 数字はコードが計算し、モデルは言葉だけを選ぶ

家計簿で AI が金額を間違えるのは致命的だと考える。そこで、数字はすべてコードで計算し、モデルには文章だけを書かせることにした。

コードが「事実」の一覧を作り、モデルはその ID をトークンとして文中に書く。

```ts
export interface Fact {
  id: string;      // 'expense-total', 'cat-pace:食費' など
  label: string;   // モデル向けの説明
  display: string; // 画面に出す文字列（"¥12,400" など）
  value: number;
  tone: 'positive' | 'neutral' | 'watch';
}
// モデルの出力例: "今月の残りは {f:budget-left} です。"
```

入力の解析は `@Generable` の構造化出力で受け、カテゴリはユーザー自身のカテゴリ一覧から選ばせている。文章のほうは、表示するときに `{f:budget-left}` を `display` に置き換える。トークンの外に数字が混ざった文、存在しない ID を引いた文は捨てて何も出さない。「使いすぎ」「無駄遣い」のような責める言葉が入った文も捨てる。記録をやめたくなる一言なら、出さない方がいいと考えた。

ちなみに、モデルの出力からは em dash も機械的に取り除いている。

## Siri にはスナップショットを読ませる

Siri の App Intents は Swift で書く必要があるが、Suito の計算ロジックはすべて JS 側にある。Swift で同じ集計を書き直すと、いつか Siri とアプリで数字がずれるだろう。

そこで、JS を唯一の書き手にした。保存のたびに、記録・繰り返し記録（前後 12 か月分を展開）・月ごとの集計を JSON にして書き出し、Swift はそれを読むだけにしている。

**Siri の答えも、アプリの画面と同じ関数で計算した数字になる。**

Siri から記録を追加した場合は、別の inbox ファイルに追記し、次にアプリを開いたときに JS 側でマージする。

最初は App Group で共有するつもりだったが、App Intents をメインのアプリターゲットにコンパイルすれば、アプリ自身の Documents ディレクトリをそのまま使える。entitlement もプロファイルも変えずに済んだ。

## プライバシーで決めたこと

Suito の App Store のプライバシー表示は「データの収集なし」である。1.1.0 でもこれを守ることを前提にした。

- 音声認識は `requiresOnDeviceRecognition = true` で、端末内の認識器がない言語では使えないようにした
- レシートの画像はメモリ上だけで扱い、保存しない
- Spotlight の索引は iPhone の中だけ。設定から切ると索引も消える

Apple には iOS 27 から Private Cloud Compute のより大きなモデルもある。ただ、アプリからのリクエストがデータ収集に当たるのかを確認できなかったので、1.1.0 ではその切り替え自体をコンパイルから外した。確認できてから入れればいいと考えている。

もっと賢い AI に聞きたい人には「ChatGPT で聞く」を用意した。アプリが計算した集計を入れたプロンプトを先に見せ、共有シートで渡す。送るのはユーザー自身で、Suito からは何も送らない。

## Liquid Glass は自作しない方がよかった

1.0.1 では、下のタブバーを iOS 26 の Liquid Glass に合わせようとした。

最初は自前のカプセルの中に `expo-glass-effect` の GlassView を置き、選択中のタブのレンズを JS のバネで動かしていた。6 回作り直したが、どれもネイティブには見えなかった。屈折やレンズの変形は `UITabBar` 自体が持っている効果で、自分のレイアウトの中に GlassView を置いても平らなガラスにしかならないようだ。

最終的に `react-native-bottom-tabs` で OS の `UITabBar` をそのまま使うことにした。中央の ＋ は system タブの間に置けないので、`role: 'search'` のタブとして横の丸ボタンにしている。真ん中に置けないのは妥協だが、本物のガラスの方を優先した。

見た目の調整に時間を使うより、OS の部品を借りる方が早いと感じた。

## 実機でしか分からないこと

Web では端末内モデルも、ネイティブのタブバーも動かない。レイアウトは Playwright で押さえつつ、モデルの答えの質、Siri のフレーズ、Spotlight は TestFlight で確認している。

temperature については、音声メモアプリのときに慎重すぎるプロンプトを 0.1 で動かしたら、実機で何も返ってこなかったことがある。今回は入力の解析を 0.2、手紙や一言を 0.4 にして、そのあとの後処理はコードで決定的に行うようにしている。

## おわりに

端末内モデルは大きなモデルほど賢くはない。ただ、家計簿のように数字をコードが持てるアプリなら、モデルに任せるのは「言葉を選ぶ」部分だけで十分だと考える。

Suito は無料で、広告もアプリ内課金もない。AI 機能は Apple Intelligence 対応の iPhone で使える（Siri と Spotlight は iOS 26 以降の iPhone ならどれでも）。気になった方は触ってみてもらえると嬉しい。
